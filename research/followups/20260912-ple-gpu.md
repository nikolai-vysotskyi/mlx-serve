# Zero-copy GPU PLE: component win, rejected model integration

A current mixed-model profile at the HC-corrected head found PLE host gather taking 1788.11 ms on the first 8192-token chunk and 488.67 ms on the second, after the background 29.8 GiB page-cache warm pass had completed. The profiler synchronizes per block, so these are attribution observations, not throughput comparisons. See `mixed-forward-profile.txt`. The existing [CPU-thread PLE PR #375](https://github.com/ddalcu/mlx-serve/pull/375) already documents fault-sensitive gains and small steady-state model effects; forcing its existing pread pool is not the proposed change.

## Implemented approach

`ple-mmap-gpu-probe.mm` wraps the original read-only `ngram_table.bin` mapping in a Metal buffer with `newBufferWithBytesNoCopy`. The returned contents address equals the mmap address; no CPU copy of the whole table is requested. A GPU kernel selects and dequantizes affine4/gs32 rows and applies the same explicit BF16 RNE packing as the host. The table, weights, hash row IDs and precision are unchanged.

The standalone component uses the actual 320,001,536-row, 160-column mixed-checkpoint table, with 131,072 seeded random row IDs (the row count for 8192 tokens × 16 heads). It compares against a C++ scalar CPU reference implementing the host formula, **not the compiled Zig production gather**. All 20,971,520 BF16 elements match exactly.

| Observation | Time |
|---|---:|
| Wrap original mapping (same address) | 1.10 ms |
| First CPU pass | 4071.22 ms |
| First GPU pass after CPU | 7029.68 ms |
| Warm CPU reference, before / after | 53.3005 / 53.1516 ms |
| Warm GPU, median of three | **1.47779 ms** |

The warm component ratio is about 36×. First-use preparation is expensive and the Metal buffer registers 32,000,153,976 file bytes (rounded to pages). The component was run without model weights resident. It does not establish model throughput or characterize cold SSD/PTE behaviour equivalently between arms.

## Model integration and outcome

`ple-gpu-integration.patch` applies to production head `1b1a4df`. It uses MLX's explicit no-copy allocator API and refuses a copy fallback, retains mmap ownership until the MLX array is released, accounts the table in MLX active memory, checks a two-GiB scratch reserve against its memory limit, and validates three real rows against native CPU output during model load. Unsupported geometry, insufficient budget and startup parity failures retain the CPU path. At prefill width the GPU result is copied into the existing packed BF16 leaf; decode retains the host route. The flag `MLX_SERVE_PLE_GPU=1` is opt-in.

ReleaseFast built successfully. A separate MLX bridge check passed 480 exact BF16 elements; startup took 2.028 s in that component process. The actual model test used the same experimental binary for both arms, all three existing fusions on, fixed public-source prompts, greedy seed1234, prefix caching/MTP/PLD off, chunk8192 and ctx131072. The on log proves GPU PLE engagement.

| Prompt | GPU PLE off | GPU PLE on |
|---|---:|---:|
| 13,515 tokens | 1553.8 tok/s | 1001.8 tok/s |
| 15,715 tokens | 1987.7 tok/s | 1075.6 tok/s |
| Model readiness incl. load/warmup | 19.24 s | 82.01 s |

Both arms returned the exact same passphrase with zero cached prompt tokens. This is a single OFF/ON HTTP pair, not llmprobe and not a precise causal estimate. The regression is sufficient to reject the integration; no repeated long run was justified. The large extra GPU registration and interaction with model residency are plausible explanations, **not isolated counter measurements**. There is no accepted whole-model improvement.

The prototype is removed from the runtime branch; its patch, source hashes, binary fingerprint and HTTP evidence remain in `ple-gpu-http-ab.json`. The production PR stays at the tested HC correction. No full Zig suite was spent on the rejected PLE integration and no new PR claims it is ready.

## Reproduce component

```sh
clang++ -O3 -std=c++20 -fobjc-arc -ffp-contract=off -mmacosx-version-min=26.3 \
  research/followups/ple-mmap-gpu-probe.mm -framework Foundation -framework Metal \
  -o /tmp/ple-mmap-gpu-probe
# Hold the exclusive GPU lock. Model servers should be unloaded for this standalone cell.
/tmp/ple-mmap-gpu-probe /path/to/ngram_table.bin
```

For model reproduction, apply the archived patch to `1b1a4df`, build on the target Mac and toggle only `MLX_SERVE_PLE_GPU`. Account startup time and memory separately; do not report the standalone warm 36× as a model gain.

## Next implementation direction

Keep only selected immutable PLE rows in a bounded cache, deduplicate row IDs before faults/dequantization, and overlap preparation of the next prompt chunk with the current GPU forward. This avoids registering the entire table. Preserve the exact row hash/history, BF16 packing and caller-visible output ordering; embedding memoization must not be confused with prefix/KV cache hits. Measure one component first with realistic unique-row and hit counts, and account cold misses. Combine useful PLE savings with the counting-grouped MoE reduction; neither current result establishes the requested >1.5× whole-model target.

## Follow-up: regression investigation and bounded successor

The integration was investigated further rather than treating its slowdown as a property of GPU PLE. [Detailed findings](20260912-ple-residency-investigation.md) identify the skipped CPU warmer, whole-table first-use page-ins, large memory-residency effects, and multi-second command overhead despite sub-millisecond GPU work in a separate-queue attempt. A new selected-row staging fixture uses 13.1 MB and measures 16.54 ms versus 54.25–54.74 ms for its C++ CPU reference, with exact BF16 outputs. No new whole-model speedup is claimed.
